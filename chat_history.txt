Provide solition approach for the hackathon

My recommendation: don’t compete on summarization. Every team will build “upload PDF → summary → RAG chat”. Win on traceability and cross-document compliance checks. Those map to the hardest pain points in the brief (error-prone cross-referencing, compliance gaps), and most teams will skip them.

Positioning
“TrialLens: every answer cited, every inconsistency caught.”

Three things that make it stand out
Citation-first summaries. Every summary sentence links to the page and paragraph it came from, and clicking it highlights the source. A second LLM pass checks each sentence against its source and drops anything unsupported. That gives you a concrete answer to “high accuracy”.
Cross-document consistency checker (the main feature). It pulls the same items from the Protocol, Consent Form and regulatory submission (inclusion/exclusion criteria, dosing, visit schedule, risks) into a JSON schema, then compares them. Example output: “Consent form lists 6 visits; protocol v2.1 lists 8.”
Role-based summary views. The same document gets a different summary for Regulatory, Clinical Ops and Medical reviewers, each following a template based on ICH E6/E3 sections. It also shows role-based access visibly instead of just stating it.
Optional extra: amendment diff, which summarizes what changed from Protocol v1 to v2 and what that affects.

Architecture (kept simple)
Ingestion: connector to the document management system (a mock API is fine) or upload → PyMuPDF to extract text → chunking by section heading → metadata (study, phase, doc type, version)
HIPAA gate: Presidio de-identification runs before anything reaches the LLM, and redaction counts are logged
Store: pgvector, with role tags as metadata filters so access control is enforced at retrieval time
LLM: a pretrained model through a private endpoint (Azure OpenAI or Bedrock) with zero data retention. No fine-tuning, which matches the constraint.
Retrieval: hybrid BM25 plus vector search. Medical terms and drug names need exact keyword matching.
Audit: hash-chained, append-only log of who asked what, which chunks were used and the model version. This makes it tamper-evident, in the spirit of 21 CFR Part 11 and GxP.
UI: React or Streamlit with three tabs: Summary, Chat and Consistency Report
Data and evaluation
Generate 2–3 synthetic trials (protocol, consent form, submission) and deliberately plant 5–6 inconsistencies in them
Metrics: faithfulness score (RAGAS), share of planted gaps detected, and review time compared with a manual baseline
Demo flow (5 minutes)
Upload → the de-identification gate fires → role-based summary with clickable citations → chat query → consistency report finds the planted gaps live (this is the high point) → audit log view → switch role and show an access denial.

Checking which caching layers each provider supports
Use context caching at four levels. Together they make cost and latency fall as usage grows, and because every cache key includes the document version, nothing goes stale.

The four cache levels
Level	What’s cached	Key	What it saves
1. Prompt-prefix cache (provider side)	The fixed start of each prompt: system prompt, role template, tool definitions and a “study context pack”	Identical prompt prefix	Cheaper, faster input tokens on every call
2. Semantic answer cache	Final answers with their citations	role + study + document versions + question embedding (similarity ≥ 0.92)	The whole pipeline: no LLM call at all
3. Summary and fact cache	Section summaries and extracted facts	doc_id + version + section hash + prompt version	Re-summarizing the same document for every role
4. Embedding cache	Chunk vectors	SHA-256 of the chunk text	Re-embedding unchanged text when a document is re-ingested
Plus conversation memory compression: keep the last 2 chat turns word for word and a ~150-token summary of older turns (written by nano), instead of resending the whole chat history.

Level 1: structure prompts so the provider can cache them
OpenAI-family models (including the Azure ones in your .env) cache long prompts (roughly 1,000+ tokens) automatically when the beginning is byte-identical, and repeated input is billed at a discount. Order every prompt like this:

[STATIC, identical across users] system rules → role template → tool definitions
                                 → study context pack (all section summaries, ~3K tokens)

Level 2: version-aware answer cache

def cache_key(role, study, doc_versions):           # e.g. {"PROT":"v2.1","ICF":"v1.3"}
    return f"{role}|{study}|" + "|".join(f"{k}:{v}" for k, v in sorted(doc_versions.items()))

hit = ans_cache.query(query_embeddings=[qvec], n_results=1,
                      where={"key": cache_key(role, study, vers)})
if hit["distances"][0] and 1 - hit["distances"][0][0] >= 0.92:   # cosine similarity
    return hit, "cache"   # answer, citations and original trace id
When Protocol v2.2 is uploaded, the key changes and every old cached answer misses automatically. There’s no manual clearing step and no stale answers.

Each cache entry records the prompt version, so changing a prompt also invalidates the cache.
